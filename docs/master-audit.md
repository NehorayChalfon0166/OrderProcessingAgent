# Master Branch Audit — Issues & Gaps

Audit date: 2026-06-16  
All core files, CLI simulations, and edge cases tested.

> **2026-06-17 update:** Issues #1 (COMPLETED), #2 (PAYMENT_PENDING dead-end),
> #3/#5 (empty/stale text) resolved via loop-based agent and payment infrastructure.
> See `docs/agent_loop.md` and `docs/payment_architecture.md`.

---

## Critical

### 1. COMPLETED transition never implemented

`confirm_order` sets `_pending_transition = PAYMENT_PENDING`. `_apply_transition`
handles PAYMENT_PENDING correctly, but there is NO handler for COMPLETED.
The state machine says BUILDING → REVIEW → PAYMENT_PENDING → COMPLETED, but
COMPLETED falls through to the fallback and is silently cleared. An order can
never reach the COMPLETED state.

The docs confirm this is intentional ("TBD — when we add a payment webhook")
but it means no order ever finishes.

**Location:** `agent_loop.py` lines 164-172  
**Root cause:** The COMPLETED transition was designed for an external payment
confirmation that was never added.

### 2. PAYMENT_PENDING is a dead-end state

`TOOLS_BY_STATE` for PAYMENT_PENDING: only `view_cart` and `cancel_order`.
Once the order enters PAYMENT_PENDING, the customer can only look at it or
cancel. There's no path forward. Related to #1.

## High

### 3. Empty text with tool calls → user sees nothing

The single-call loop records the LLM's text BEFORE executing tools. If the
LLM returns `content=""` with `tool_calls=[...]`, `process_turn` returns `""`.
The customer gets radio silence. The tool executes (item added) but they
don't get told "Added!" until the NEXT user message, which triggers a second
LLM call that sees the tool result.

**Observed on Twilio integration, same root cause applies to master.**  
**Location:** `agent_loop.py` lines 57-64  
**Root cause:** Single-call pattern — LLM text is returned before tool
results are available. The LLM sometimes chooses not to include text when
making tool calls (varies by model and message context).

### 4. Menu dump on greeting

First "Hi" produces a 200+ word response listing every menu category with
items. The prompt provides menu hints (e.g. "Pizzas: Margherita, Pepperoni,
...") and the LLM treats them as content to narrate rather than context to
reference.

**Location:** `prompts.py` line 42 — `Menu categories: {hints}`  
**Root cause:** No instruction to keep greeting brief or to only mention
menu when asked. The hints are presented as a labeled list, which the LLM
faithfully reproduces.

### 5. Single-call loop: "Adding..." → silence → "Added!" requires two turns

When the LLM says "Let me add that!" AND calls `add_to_cart` in the same
response, the tool executes and state updates, but the LLM doesn't see the
result until the next turn. The customer sees "Let me add that!" but must
text again to trigger the response that says what was actually added.

**Location:** `agent_loop.py` — the entire `process_turn()` flow  
**Root cause:** Tool results are appended after the LLM's text is returned.
The LLM responds based on the PRE-tool-execution state, not the post state.

## Medium

### 6. Verbose, unnatural responses

No brevity instruction in the prompt. The LLM defaults to:
- Multi-line marketing text
- Emojis before every message
- Repeating the menu when not asked
- Overly polite filler ("I'd be happy to help you place an order")

**Root cause:** `prompts.py` has zero tone or brevity guidance.

### 7. Prompt gives no state-specific instructions

Same prompt for BUILDING, REVIEW, PAYMENT_PENDING. The LLM doesn't know
the difference between "ask for confirmation" (REVIEW) and "confirm the
order" (PAYMENT_PENDING). It sometimes calls `view_cart` when the user
says "confirm," or calls `request_review` when it should call `confirm_order`.

**Root cause:** `build_system_prompt` shows `session.state.value` as a
bare string with no explanation of what that state means or what behavior
is expected.

### 8. Greeting is generated by LLM via process_turn("Hi")

`run_session()` calls `process_turn(session, "Hi", ...)` to generate the
greeting. This is the LLM's first turn — it has no context, an empty cart,
and menu hints. The result is unpredictable: sometimes a welcome message,
sometimes "How can I help?", sometimes a full menu dump.

**Root cause:** The greeting should be a short, deterministic template
(or a separate prompt that constrains the LLM to a simple greeting).

### 9. Session router terminal-state check uses bare import

`session_router.py` has `from models import OrderState` and checks
`session.state in (OrderState.CANCELLED, OrderState.COMPLETED)`. This is
correct behavior, but it relies on the session file being readable and
the state enum being importable. If the `models` module changes the enum
values, this silently breaks.

**Risk: low, but fragile.**

## Low

### 10. No session persistence between CLI runs

Each `python main.py` creates a new `OrderSession()`. The session is saved
to disk but never loaded. If the user runs the CLI, quits, and runs it
again, they get a fresh session even if their previous order was in REVIEW.

**This is by design for CLI mode**, but worth noting. The `session_router`
solves this for server mode.

### 11. `_apply_transition` has dead fallback path

The fallback `session._pending_transition = None` at the end of
`_apply_transition` was written as a safety net for unknown transitions.
With COMPLETED missing, this fallback is the ONLY handler for COMPLETED
— it silently clears the transition and the order dies.

### 12. No tests for COMPLETED or PAYMENT_PENDING exit

Test suite covers REVIEW blocking conditions (empty cart, no name, no
phone) but has no test for PAYMENT_PENDING → COMPLETED. This is expected
since COMPLETED was never implemented.

## What Works Correctly

- Multi-user session isolation
- Cancel flow (cancel_order → CANCELLED from any state)
- CANCELLED sessions auto-replaced by router
- Tool dispatch and error handling
- State gating (tools restricted by state)
- Cart operations (add, remove, update)
- Customer info merging
- Pricing engine
- Catalogue fuzzy matching
- REVIEW preconditions (cart empty, no name, no phone, delivery no address)
